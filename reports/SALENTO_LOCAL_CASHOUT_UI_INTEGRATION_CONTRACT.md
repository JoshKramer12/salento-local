# Salento Local — Cash Out UI integration contract

**Stage 10F documentation only. No UI changes were made.** The existing Partner dashboard and Earnings page already call `getPartnerCashoutView(page)` and server actions in `src/app/(account)/dashboard/earnings/cashout-actions.ts`; future design work should consume these backend contracts rather than infer financial eligibility in the browser.

## Read model

`getPartnerCashoutView(page)` is session scoped to a profile-complete `GETTER`; other roles fail with `partner_cashout_not_authorized`. It returns integer EUR cents: `availableCents` (net eligible, unreserved and debt adjusted), `pendingCents`, `reservedCents`, `paidCents`, `grossEarnedCents`, `debtCents`, `testCents` and `unverifiedCents`. Historical TEST and unknown-mode credits are display-only and cannot be withdrawn. `minimumCents=5000`. `destinationReady`, masked `destinationLast4` and `bankName`, `activeWithdrawalId/status`, `unresolvedLegacyPayoutId`, `requestEnabled`, and `disbursementsAllowed` determine whether a request is possible. A positive `availableCents` alone is insufficient: the flags, destination, active slot and minimum must all pass. The `cashoutBlockReason(view)` presenter returns `paused`, `review`, `active`, `debt`, `pending`, `minimum`, `destination` or `null`.

`history` is a newest-first, owner-scoped page of ten withdrawals with `id`, `amountCents`, `status`, `requestedAt`, `completedAt`, masked destination and `canCancel`; `page`/`hasMore` support pagination. `legacyHistory` is separate. Withdrawal statuses are `REQUESTED`, `READY_FOR_PROCESSING`, `PROCESSING`, `PAID`, `CANCELED`, `INVALIDATED`, `ACTION_REQUIRED`, `FAILED_CONFIRMED`, `OUTCOME_UNKNOWN`. `PROCESSING` means a provider operation is in progress; `PAID` is a verified provider payout state and still needs ongoing failure/statement monitoring, not proof of bank arrival. `ACTION_REQUIRED` and `OUTCOME_UNKNOWN` require operator reconciliation; the UI must not offer a blind retry.

The Cash Out view does **not** include each commission's `eligibleAt`. Existing dashboard commission-ledger data supplies it for hold progress. If a redesigned Earnings panel needs itemized dates, pass the existing ledger projection or add a read-only server projection during the separate UI task. Do not compute eligibility solely from the displayed date: the server also checks `Payment.paidAt`, paid status, refund state, provenance, attribution, debt and reservation.

## Mutations and authorization

`submitCashoutRequest(requestKey, reviewedAmountCents)` is the server action. Use a client-generated 16–128 character idempotency key and the amount the Partner reviewed. It returns `submitted` with request ID/amount/status/masked destination, `changed` with a fresh available amount and `newKey` guidance, `unavailable`, `invalid`, `unauthorized` or `error`. The transactional backend reserves the **whole** eligible balance; the client amount is a comparison and cannot choose another Partner or override eligibility. Preserve the same key after an ambiguous browser response; use a new key only when the action reports `newKey: true` or after explicit new authorization. Do not auto-submit again after a generic error.

`cancelCashoutRequest(withdrawalId)` returns `canceled`, `processing`, `unavailable`, `invalid`, `unauthorized` or `error`. Only the owning Partner may cancel before provider processing. The backend independently rechecks session role/profile, row ownership, state and reservation. The withdrawal worker/reconciliation routes are internal bearer-protected operator interfaces, never browser endpoints. The new `GET /api/internal/partner-withdrawals/health` uses a separate monitor bearer and returns read-only incidents; it is not a Partner API.

## Feature behavior

`PARTNER_CASHOUT_UI_ENABLED` controls visibility. Requests require that flag, `PARTNER_CASHOUT_REQUESTS_ENABLED`, and an execution-ready processor; this coupling prevents collecting requests when the worker is paused. Worker execution requires its separate processing gate, legacy payout execution off, eligible LIVE payment mode and worker authentication. Retry/reversal operator gates remain separate and default off. The UI should render pending, available, reserved, paid, debt, TEST and unknown amounts distinctly, respect the backend block reason, mask destinations, and never imply that a Stripe transfer is a bank deposit. The later UI task owns copy, layout, accessibility and EN/IT behavior.
