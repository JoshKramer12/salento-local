# Salento Local — TEST-to-LIVE transition plan

**Plan only, 20 November 2026. No production or Stripe change is authorized.** Use the prepared Stage 10E code on `feature/stage10e-live-readiness` only after an exact-commit release review. The first transaction is a bounded manual-card canary on the production web service; do not switch all visitors to unrestricted payments or turn on Cash Out.

## Why the transition needs gates

Stripe TEST and LIVE keys address separate Customers, subscriptions, payments and webhook secrets ([Stripe API keys](https://docs.stripe.com/keys)). Production currently has 12 active TEST automatic subscriptions, one additional retrievable TEST subscription, one stored subscription lookup failure, 18 pending provider-linked payment rows, and 86 Payment rows with unknown mode. Merely swapping keys would strand TEST objects and make historical reminders misleading. The new code rejects old provider-object reuse, pauses the membership cron in canary scope, and prevents TEST/NULL commissions from becoming live payable. Historical rows and listings are preserved.

The first named canary **does not require rewriting the whole historical ledger**. It does require a fresh submission with no old Stripe references, a short TEST-payment freeze, the prepared code deployed with flags off, and the canary configuration below. Broader LIVE billing later requires an owner communication and TEST-subscription disposition, an audit mapping for any locally cleared IDs, pending-object reconciliation, and provenance-aware cron/receipt review. Never bulk-mark unknown rows LIVE or cancel a Stripe subscription through LIVE credentials.

## Configuration states and ownership

| State | Stripe key pair / platform webhook | Production payment switches | Cron and Cash Out |
|---|---|---|---|
| Current | TEST/TEST + TEST signing secret | `PRODUCTION_STRIPE_TEST_PAYMENTS_ENABLED=true`; `PUBLIC_LIVE_PAYMENTS_ENABLED` off | Existing cron active; Cash Out all off |
| Prepared release | Same TEST configuration | Same as current | New code deployed; existing behavior retained |
| LIVE closed | Verified LIVE secret/publishable pair and matching LIVE platform signing secret; TEST payment switch **false** | `LIVE_PAYMENT_SCOPE=canary`, `LIVE_PAYMENT_CANARY_SUBMISSION_ID=<approved new submission ID>`, `PUBLIC_LIVE_PAYMENTS_ENABLED=false` | Cron returns `pausedForLiveCanary`; all Cash Out gates and secrets remain off |
| One-payment window | Same LIVE configuration | Change only `PUBLIC_LIVE_PAYMENTS_ENABLED=true` under separate approval | Only the named manual-card submission can create a provider payment; bank/recurring/renewal paths and Partner disbursement remain blocked; cron remains paused |
| Closed after canary | Keep LIVE keys/webhook for signed late events and refund investigation | `PUBLIC_LIVE_PAYMENTS_ENABLED=false`; keep canary scope | No new charge; verified LIVE settlement still runs; cron remains paused until historical obligations are reviewed |

`LIVE_PAYMENT_SCOPE=public` is a **later, separately approved broad launch** setting. In production LIVE mode, missing or invalid scope keeps the public creation gate closed. Do not set `public` for the first transaction. All environment changes require founder approval and secret handling through Railway/Stripe's secure UIs, not chat, Git or reports. No Connect webhook or withdrawal worker secret is needed for the first charge.

## Exact release and activation sequence

1. **Read-only preflight:** verify latest Git/Railway SHA, code diff, TEST/LIVE flags, subscription and pending-object counts, cron services, database integrity and upload inventory. Choose one real, consenting Owner, one Partner with agreed commission terms, and a truthful business listing. Privately record their internal IDs. Verify the new submission has no Payment, Customer, Subscription, Checkout, PaymentIntent or bank instruction from TEST/unknown mode. Confirm the €100 price, manual renewal selection, agreement/signature and Partner attribution.
2. **Account-owner review:** securely verify the intended LIVE Stripe account ID, legal country/entity, charges enabled, verification requirements and restrictions, EUR card eligibility, settlement/bank setup, key/account pairing, refund support and who handles disputes. A TEST-mode Italian/EUR response does not count. Confirm any related-party or self-payment complies with the account's terms before choosing the payer. Confirm the support/receipt and Partner commission accounting process. Stop if any mandatory LIVE account field or identity is unknown.
3. **Deploy prepared code, disabled:** review and approve the exact Stage 10E commit. Create a fresh consistent SQLite online backup **and uploads archive** outside the Railway volume, hash them, restore in isolation, validate migrations and counts. Deploy the exact code SHA with existing TEST keys and every money-moving flag off. Verify Stage 10D behavior and production health. This stage is separately authorized; this plan alone does not authorize it. Railway's `railway.toml` format has a [1 December 2026 cutoff](https://docs.railway.com/config-as-code); migrate its configuration in a reviewed release before relying on deployments after that date.
4. **Freeze and inspect TEST activity:** under separate approval, stop new public TEST payments (`PRODUCTION_STRIPE_TEST_PAYMENTS_ENABLED=false`) while keys are still TEST; inspect in-flight test sessions/intents and account/Owner communications. Do not delete 89 Payment rows, 75 commissions or 21 memberships. Keep a restricted mapping of the 14 stored subscription IDs and identify the one lookup failure. The 12 TEST subscriptions continue at Stripe until separately canceled/segregated with appropriate consent. Their next recorded terms are Sep–Oct 2027; verify dates again before activation. Do not claim the freeze cancels an already-open Stripe payment page.
5. **Prepare LIVE with creation closed:** with explicit config approval, set matching LIVE keys, the LIVE platform webhook secret, `LIVE_PAYMENT_SCOPE=canary`, the approved `LIVE_PAYMENT_CANARY_SUBMISSION_ID`, and keep `PUBLIC_LIVE_PAYMENTS_ENABLED=false`. Recheck Railway's exact deployment SHA, key-prefix pairing, account identity via read-only `GET /v1/account`, database/upload baseline, no unintended flag, and the cron's `pausedForLiveCanary` response. Register or verify a LIVE platform endpoint at `https://web-production-6f26e.up.railway.app/api/stripe/webhook` with the ten event types listed in the readiness report; store only its signing secret in Railway. Verify endpoint identity, signing-secret match and a Stripe-supported nonfinancial LIVE delivery before opening payments. A local signed mock proves code validation only; if provider-originated LIVE delivery cannot be verified safely, stop for a new decision. Keep TEST and LIVE webhook secrets distinct. Do not create a LIVE Connect endpoint for this payment.
6. **Authorize one charge:** the founder separately approves exactly one €100 manual-card payment for the named Owner/business/Partner, maximum exposure and operator window. Only then change `PUBLIC_LIVE_PAYMENTS_ENABLED=true`, verify no other creation path is open, and perform the canary described in `SALENTO_LOCAL_FIRST_REAL_100_EUR_CANARY.md`. Check Stripe's actual `livemode=true`, amount/currency/status and account, the signed event, one paid Payment, membership, one pending €50 commission and delivery state before any second action.
7. **Close and observe:** set the public creation flag false after the confirmed canary while keeping LIVE keys and webhook available for delayed signed events, refunds and reconciliation. The prepared finalizers can settle a verified LIVE payment even after new creation is paused. Review payment/commission/receipt and provider logs; do not switch back to TEST keys while LIVE payment effects are unresolved. Resume cron and broad payments only after a separate historical-data and queue plan.

## Historical records and later full launch

Retain TEST/NULL Payment, commission, membership and provider references as audit data; never count them as real revenue or payable cash balance. Cash Out queries require an explicitly LIVE paid Payment and the hold. For each old automatic subscription, verify provider ID/status under TEST, identify the Owner and accepted terms, decide communication and provider cancellation separately, and only after Stripe confirmation update local `automaticRenewal`/`recurringPaymentReady`/subscription status under an approved data runbook. Preserve the old ID mapping before any local field clear. Decide whether each historical listing remains entitled through its recorded term; do not revoke listings as a side effect of a key switch. Review pending test Checkout and bank intents, failed-payment/outcome queues and receipts before resuming cron or enabling `LIVE_PAYMENT_SCOPE=public`. A new LIVE subscription requires the Owner's explicit authorization and new LIVE Customer/Subscription IDs.

## Stop and rollback

- **Before any real charge:** if account, key pair, webhook, backup, SHA, role ownership, canary ID or gate differs, keep the creation flag false. Restore prior TEST configuration only under an approved config change after confirming no LIVE provider event or pending payment exists.
- **After a real charge or unknown outcome:** first close `PUBLIC_LIVE_PAYMENTS_ENABLED`; preserve LIVE key and webhook intake, provider IDs, signed-event logs, SQLite and uploads. Reconcile Stripe against the exact local Payment, membership and commission. Do not blindly retry, refund, cancel, clear IDs, restore a database or revert to TEST credentials. Each provider correction requires separate approval.
- A code rollback must retain a version able to process in-flight LIVE signed webhooks. Neither code rollback nor a key change reverses a Stripe charge. A database restore can erase evidence of a real provider effect and requires its own reconciliation and authorization.

**Separate Cash Out release:** only after a real commission passes its full 14-day hold, the legal/Partner obligation is agreed, live Connect/destination/funds are verified, monitoring and reconciliation are operational, and a named €50 withdrawal is approved. None of those controls should be enabled by the €100 canary.
