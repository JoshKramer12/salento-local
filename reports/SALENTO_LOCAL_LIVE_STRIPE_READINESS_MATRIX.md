## Mode-sensitive application paths

| Path | Current safeguard / remaining transition task |
|---|---|
| Checkout and PaymentIntent creation | Local Stage 10A guards reject retrieval/reuse of a pending test or untagged provider object with live credentials and persist mode for newly created Checkout/bank-transfer rows. Verify all embedded/subscription setup paths on a restored isolated copy before any key switch. |
| Customer creation and bank instructions | Stripe customer IDs and customer-balance instructions are mode-specific. Existing pending bank intents must be resolved or abandoned through an approved plan; never reuse an old customer ID under a live key. |
| Webhooks and payment reconciliation | Platform and Connect signatures use separate endpoint secrets. Event mode, exact object, amount and metadata must match local records. Keep the historical test endpoint/renewal obligations explicitly managed during transition. |
| Membership activation, renewal, reactivation and Pay Later | Business entitlements and accepted terms remain in SQLite. A live-key switch must not make old test subscriptions/PaymentIntents appear absent and create a second payable path. Stage 10A local renewal-recovery guard blocks unknown historical subscription provenance before provider retrieval. Review Pay Later invitations and bank instructions against old payment IDs before activation. |
| Automatic renewals | Twelve active test subscriptions may continue billing within test mode regardless of the site's new live key. A credential swap is not a cancellation. Separately review scheduled renewal dates, consent, notification and webhook handling. |
| Refunds, disputes and commissions | Live Owner refunds have their own release gate. Initial €50 commission remains held 14 days; eligible Cash Out must derive from a verified live Payment and account for reversals/debt. €15 renewals/reactivations must be tracked separately. |
| Receipts, invoices and dashboards | Historic test/NULL rows must retain provenance labels; Owner history, Partner Earnings and Admin payment views must not imply those records are live money. Review receipt/invoice delivery and tax/legal copy for the first live canary. |

**Approval boundary:** A future disabled-by-default code deployment is a separate decision from live credential changes, live payment authorization, Connect onboarding and every Cash Out activation step. No live provider claim is inferred from test-mode GETs.
