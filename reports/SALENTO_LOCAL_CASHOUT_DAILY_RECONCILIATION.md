# Salento Local — daily independent Cash Out reconciliation

**Prepared 19 November 2026.** This procedure is for a future activated service. It is read-only until a separately approved correction. A Stripe balance API response is a snapshot, **not** an independently signed financial statement or bank confirmation.

## Daily close (named financial owner; independent reviewer)

1. Freeze a read-only SQLite backup or consistent snapshot; record UTC cutoff, deployment SHA, schema migration count, integrity and foreign-key checks. Preserve the previous close. Read `PartnerWithdrawal`, attempts/events, payout, commission allocations, original Payment mode, refund/debt, legacy payout/run and Connect webhook log. Never run a send-capable worker as part of this step.
2. Retrieve a complete provider inventory from Stripe in the same account and mode: all platform transfers, every connected payout, reversals and associated balance transactions since an activation timestamp preceding the first withdrawal. Enumerate all relevant connected accounts. Record pagination completion, object counts and API errors; abort the close on a truncated window, inaccessible account, rate-limit/API failure or >2,000-object scanner limit. Use overlap around the cutoff and compare previous-day IDs so delayed events cannot disappear.
3. Compare **provider-first** and **ledger-first**: transfer and payout IDs, metadata withdrawal/payout IDs, connected account, exact external destination, amount, EUR, mode, status, idempotency attempt, reversal amount and failure balance transaction. Detect absent local/provider objects, duplicates, partial/full reversals, payout returned funds, late failed/canceled status, provider paid/local unsettled, and local PAID/provider not paid. A payout is not settled solely by webhook delivery; retrieve current provider state.
4. Reconcile commission allocations and reservation totals against each withdrawal. A paid withdrawal needs matching PAID payout and paid commissions; canceled/confirmed-failed cases need documented release rules. Check refund/dispute reversals and recovery debt, initial 14-day hold, and verified `Payment.stripeLivemode=true`. Reconcile the 19 legacy FAILED and 12 historical ACTION_REQUIRED rows separately; do not fold them into a new withdrawal total.
5. Obtain an independently exported Stripe balance-transaction/financial report for the platform **and each connected account**, including opening/closing balances, charges, transfers, transfer reversals, payouts, payout returns, fees, reserves, refunds and disputes. Where available, compare external bank settlement/return statements. Map every movement to a provider object and local obligation, including unrelated membership activity. A balance snapshot cannot explain an unexplained movement. Check opening + inflows − outflows = closing by currency and account.
6. Record a dated close packet: inventory scan result, provider export version, bank evidence availability, local snapshot checksum, unmatched-item list, owner, reviewer, approvals and next action. Mask bank/customer details in operational notes. Retain source artifacts under restricted access and do not commit raw exports.
7. If any financial variance, missing provider access, incomplete pagination, stale webhook or missing scan exists, mark the day **open**, page the financial owner and pause new Cash Out requests/sends under incident approval. Preserve in-flight reservations. Close only after documented provider/statement evidence and independent review; any refund, retry, reversal or SQLite correction requires separate authorization.

## Coverage of current local scanner

| Detection | Current automation | Required independent evidence / limitation |
|---|---|---|
| Stripe transfer/payout absent from SQLite, and SQLite ID absent from Stripe | Provider inventory enumerates transfer and connected payout lists; compares recorded IDs and attempts. | Account list must be complete; old objects outside `since` are excluded; scan fails closed if local withdrawal predates window. Provider API logs may be needed after unknown create outcome. |
| Wrong account, destination, amount, EUR or mode | Exact comparisons; Stage 10A adds connected payout external destination and account capability/requirements checks. | Read masked bank destination directly from Stripe and require two-person signoff before first live payout. |
| Transfer reversal, payout failed/canceled, returned funds and late failure | Reversal amount, status, failure balance transaction and local PAID conflict now emit incidents. | Balance transaction and statement prove money movement; a failed payout alone does not prove where funds sit. |
| Duplicate provider transactions | Extra provider objects with unmatched metadata/IDs trigger incidents; exact duplicate attempts reviewed. | Stripe request logs, transfer group and balance report identify intent and financial impact. |
| Commission settlement and unresolved legacy | Active allocation totals/status compared; local legacy health now flags FAILED rows and FAILED rows with payout IDs. | Historical 19-row provider reconciliation is separate manual work; local health does not itself perform provider lookups for those rows. |
| Unexplained platform balance movement | Scanner captures available/pending EUR snapshots. | **Not automated**: compare Stripe balance transaction exports and bank statements daily, including membership, fees, reserves and unrelated transfers. |

The scanner uses Stripe auto-pagination and rejects API failures, invalid mode, missing local window or count limits. It does not have a durable provider cursor, statement ingestion, rate-limit backoff or audit-grade immutable snapshot store. Those controls require a reviewed implementation and operational configuration before automated daily signoff is relied upon. The Stage 8 isolated test-mode drill matched one €50 transfer/payout and detected a genuine 1-cent reversal; it did not prove live accounting or bank settlement.
