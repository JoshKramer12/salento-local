## Stripe Connect and financial semantics (8A)

`ensurePartnerStripeAccount` creates Express accounts and requests `transfers`. The account sync attempts to set a manual payout schedule and stores account state and masked bank details. Accounts v2 can appear as `type=none` through the v1 compatibility API; `controller.stripe_dashboard.type=express` identifies the verified synthetic account. The new provider preflight reads the account and balance settings directly, requires Express, a supported country (IT/DE/FR/IE/NL/ES), active transfers, clear requirements, enabled payouts, a manual schedule, and exactly one default EUR bank. It also checks mode and the snapshotted external account identity. Any missing or inconsistent evidence stops before a transfer and retains the reservation for review. The stored dashboard READY label alone is not a release authorization.

A Partner request reserves exact eligible commissions in SQLite. A durable transfer intent precedes a Stripe transfer to the connected account. A separate durable payout intent precedes a Stripe payout from that account to its external bank. Neither the request nor transfer proves a bank payout. Only a provider-retrieved `paid` payout with matching withdrawal, attempt, amount, currency, connected account, mode and destination can settle commissions. Stripe describes `payout.paid` as expected availability and notes that a later `payout.failed` may follow: [event types](https://docs.stripe.com/api/events/types). Late conflicting evidence remains `ACTION_REQUIRED` with paid history preserved. Transfer reversal after a paid payout likewise blocks further Cash Out and requires operator review.

The Stage 5A report records a genuine test-mode €50 transfer and connected payout, plus provider idempotency and reconciliation, in a separate synthetic sandbox. Stage 8 did not repeat a money-moving provider operation. The Stage 5A payout event was previously **retrieved and signed for local replay**; it was not observed being forwarded live by Stripe CLI. That historical evidence is summarized in the accompanying verification matrix; its original external artifact remains outside this repository.

## Worker security, exactly-once effects and legacy conflict (8C, 8D, 8G)

The internal route requires a configured bearer secret and uses timing-safe comparison. Missing configuration returns 503; wrong or missing bearer returns 401. Production has no worker-secret variable. Work is bounded to ten withdrawals per invocation and guarded by leases; there is no separate request rate limiter, so scheduler access and run frequency must be controlled. The processor requires a separate execution flag and live-payment gate outside a verified local sandbox context. The request service derives Partner identity from the session, rechecks the database role, serializes changes with a Partner profile write, and uses a unique active Partner slot plus a unique Partner/request key. SQLite writes, durable attempt rows, fixed provider idempotency keys and a five-minute lease guard duplicate sends. Unknown outcomes retain reservations and must reconcile provider objects before another send. Mocked tests cover concurrent requests/workers, timeouts before and after provider success, crashes, refunds, failed/canceled payouts, reversed transfers, late conflicts, and debt.

Legacy batch and Cash Out touch the same `PartnerCommission` rows and use different reservation paths. Existing legacy reservation skips any Partner with a withdrawal, recovery, or debt; new requests reject unresolved legacy payouts. Stage 8 additionally makes the **global send flags mutually exclusive**: if Cash Out processing or requests are enabled, the legacy batch returns disabled; if legacy sending is enabled, the Cash Out processor and requests remain paused. Historical payout records remain readable. This prevents simultaneous activation but does not repair the legacy batch's ambiguous failure handling; keep its execution flag off permanently pending a separate migration/reconciliation decision.

The single owner recommendation is one secret-protected scheduler calling the existing web worker route, with one bounded processor run at a time, plus a separate read-only/reconciliation invocation. Do not add a second payout service or reuse the membership reminder cron. Railway currently has no withdrawal cron. Configure schedules only in a separately approved activation stage, after proving SQLite lease behavior and webhook recovery under an actual restarted isolated app.

## Monitoring and reconciliation (8E)

Stage 8 adds an authenticated, read-only `?health=1` scan behind the existing worker secret. It returns stable incident keys for stale requests, stalled pre-payout processing, long pending payouts, `OUTCOME_UNKNOWN`, `ACTION_REQUIRED`, stale reconciliation, reservation discrepancy, paid evidence discrepancy, and failed/stuck Connect webhook logs. Thresholds are configurable in minutes and bounded. No notification sink or production schedule is enabled. The reconciliation worker now logs a sanitized error code and withdrawal ID when provider reconciliation fails.

Current reconciliation retrieves recorded or discoverable Stripe transfers and connected payouts, verifies identities/amounts/mode, and does not create another transfer/payout. It can leave unresolved or partial transfer reversals on manual hold. It does **not** independently enumerate all provider transfers for unexpected objects, compare platform and connected balances to an external statement, persist alert acknowledgments, or verify a scheduled run occurred. Stable incident keys support downstream deduplication, but alert delivery, escalation ownership, missing-run detection, and daily independent reconciliation still require implementation and an isolated end-to-end drill. Railway logs alone are insufficient as an alerting system.
