# Salento Local — Stage 10F Cash Out backend acceptance

**20 November 2026. Classification A: backend development complete for future integration; Cash Out activation is not approved.** This is a development conclusion based on isolated tests and prior Stripe TEST evidence. It does not certify a LIVE connected account, real funds, bank arrival, or production monitoring.

## Baseline and actual gaps

This branch starts from the untouched Stage 10E local commit `c8f54be9156d65dd368b5dfab7cdb91a9b8ed22f`; the latest remote `main` and Railway `production/web` SUCCESS deployment remain `44fc39f56087e67df7ad63dc7db1fdd5b5b2b7d3` (deployment `2c9f9dd7-9d1e-49d2-bd70-947471b72f94`). Read-only Railway variable inspection found TEST secret/publishable keys, `PRODUCTION_STRIPE_TEST_PAYMENTS_ENABLED=true`, and all reviewed LIVE, Cash Out request/worker/legacy/retry/reversal gates and Connect/withdrawal worker secrets absent. There is no Cash Out scheduler. No production setting, record or provider resource was changed.

Before coding, review found extensive isolated coverage of commission attribution, 14-day hold, refund debt, atomic reservation, concurrent requests, worker leases, unknown outcomes, idempotent transfer/payout attempts, authenticated Connect webhook reconciliation, reversals, late failures and independent inventory. The two actual development gaps were (1) no single acceptance test linking Owner confirmation and payment finalization through a settled withdrawal with boundary-time checks, and (2) the prospective monitoring script needed the send worker's bearer even for its health read. No other material Cash Out backend defect was found.

Stage 10F added one end-to-end isolated acceptance scenario and exact refund-boundary tests. It added `GET /api/internal/partner-withdrawals/health` protected by `PARTNER_CASHOUT_MONITOR_SECRET`, rejecting an absent or shared worker secret; the control script now uses `PARTNER_CASHOUT_HEALTH_URL` and this distinct secret for both local health and a provider-first inventory. The inventory runs on the web service next to SQLite and uses only Stripe GETs, so a separate monitor needs neither the web volume nor Stripe/worker credentials. Tests prove the monitor bearer gets health but is rejected by the send route. These are backend changes only; no UI file, pricing, hold duration, minimum or provider gate changed. The endpoint and script are **local code only**, not an operational monitor until separately deployed and configured with durable state, an alert destination and an external missed-run watchdog.

## Provider evidence, with limits

**Fresh Stage 10F read-only Stripe TEST GETs:** the production TEST platform returned account `acct_1TqwSuRTjKpCuoPH`, country IT, TEST charges/payouts enabled, `livemode=false` balance with zero available EUR, and 49 visible connected TEST accounts (`has_more=false`). This does not establish any LIVE capability or readiness of a particular Partner destination. The earlier inventory counted fewer accounts; the cause of the increase was not established and should be reviewed before activation. All Stage 10F provider calls were GETs.

**Prior genuine TEST operations, retained evidence:** Stage 5A created an isolated EUR 50 transfer and connected payout with stable idempotency IDs. Stage 8 obtained Stripe delivery of a genuine `payout.paid` event to the isolated application route across restart, observed duplicate delivery without duplicate settlement, and created a genuine one-cent transfer reversal detected by independent reconciliation. See `SALENTO_LOCAL_CASHOUT_PROVIDER_VERIFICATION.md` and `SALENTO_LOCAL_CASHOUT_STAGE8_REPORT.md`. These were not repeated or relabeled as new Stage 10F mutations. Stripe states that TEST payouts do not send money and a payout reported paid may later fail ([payout API](https://docs.stripe.com/api/payouts/create), [event types](https://docs.stripe.com/api/events/types)).

**Still mocked or unverified at the provider:** fresh end-to-end €100 TEST payment to new €50 TEST transfer/payout, genuine `payout.failed`/`payout.canceled`, returned-funds and late-failure delivery, a network timeout after provider acceptance, database outage during webhook handling, and bank/statement settlement. The current production TEST platform has no available EUR; Stage 10F did not mutate any production-linked TEST object or fund a new sandbox. These scenarios remain an activation test or documented risk decision, not a known missing backend code path.

## Final verification and decision

The final source suite passed **708 tests, zero failures**. Application and operational-script TypeScript, Prisma schema validation, ESLint (zero errors, seven pre-existing warnings), optimized production build and `git diff --check` passed. Tests use disposable SQLite databases and mocks where identified. The new read-only monitor endpoint is authenticated and cannot send. Production Cash Out remains closed by absent gates, TEST-key disbursement hold, and no worker/scheduler.

**A — backend development complete.** The underlying ledger, reservation, provider intent/reconciliation and failure-hold behavior are sufficiently implemented and tested to move on to other website features. Activation still needs the specific operational, LIVE financial and UI gates in `SALENTO_LOCAL_CASHOUT_LAUNCH_CHECKLIST.md`. A development-complete label does not authorize a live withdrawal.
