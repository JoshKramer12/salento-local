## Financial and security controls checked in code

- Paid Payment records and valid attribution are required for earned commissions. Initial commissions retain their 14-day eligibility; paid renewal/reactivation commissions use their own payment timing. The ledger excludes unpaid submission placeholders, reserved/paid commissions, debt, open refund requests, and tracked active dispute holds from new reservations.
- Withdrawal requests reserve the full eligible amount in one database transaction with a unique unresolved-request constraint and idempotency key. The destination is encrypted and snapshotted. Dispatch rechecks the reservation, debt, refund, dispute, payment, and destination. Provider dispatch claims one request and records that dispatch began before external calls.
- Stripe transfer and payout use stable request-based idempotency keys. Transfer creation alone does not mark `PAID`. Stripe payout settlement is verified by retrieving the current payout on the snapshotted connected account. PayPal batch acceptance remains `PROCESSING`; item `SUCCESS` is required for `PAID`. Manual settlement requires an Admin confirmation and evidence. Failures and uncertain outcomes retain reservations.
- Partner and Admin routes check authenticated roles and Origin where applicable. The weekly endpoint requires `PAYOUT_JOB_SECRET`. Stripe platform and Connect webhooks require separate signature secrets and persist event-processing state. Full manual IBAN reveal requires Admin and creates an audit event. Encrypted destination and evidence require `PAYOUT_DATA_ENCRYPTION_KEY`.
- These checks do not establish that all historical production data meets the assumptions. The diagnostic and provider reconciliation gates above are mandatory.

See [the reconciliation controls and remaining accounting work](partner-cashout-reconciliation.md) for the new local implementation and unresolved release design.

## Operator reconciliation: every case starts with a hold

Record the withdrawal ID, payout ID, Partner ID, amount in cents, destination snapshot (masked unless authorized), all provider references, audit events, commission IDs/statuses, refund/dispute/debt state, and a time-stamped provider response. Do not use an unsourced screenshot as sole settlement evidence. Never mark paid because a transfer or batch was merely accepted. Keep `ACTION_REQUIRED` or `FAILED` reservations in place until a reviewed backend action exists and the external outcome is certain. No current Admin action can release a dispatched failed withdrawal.

| Case | Inspect and required evidence | Current safe action and prohibited action |
| --- | --- | --- |
| A. Stripe transfer exists, no verified payout | Retrieve transfer by ID or `transfer_group=withdrawalId` and inspect the connected account payouts by withdrawal metadata. Confirm amount, currency, destination, reversal state, payout ID/status, and account balance history. | Use Admin **Reconcile** if a payout can be attributed. For a new dispatcher row with a recorded transfer and no payout-attempt marker, Admin **Continue existing Stripe payout** can create one payout after server-side checks and a durable claim. Legacy rows and ambiguous provider records remain held. Never create another transfer. |
| B. Provider timeout, no reference | Stripe: search transfer group and payout metadata on the snapshotted connected account. PayPal: search the recorded deterministic sender batch ID, recipient, amount, and item ID in provider records. Preserve query results and time. | Admin **Reconcile** can recover a discoverable Stripe payout. A PayPal batch ID found at the provider can be attached only after the server verifies all attribution fields. If still unknown, retain `ACTION_REQUIRED`; do not resend funds. |
| C. Definitive provider failure | Retrieve the current Stripe payout/transfer or PayPal batch/item; confirm whether any funds reached the recipient or remain with the provider, including reversals. | Admin **Reconcile** records supported failures; reservation remains held. Do not cancel or retry provider dispatch. A reviewed release path is missing and must be implemented/tested after evidence and approval. |
| D. Settlement after uncertain/failed state | Retrieve current payout/item and bank/provider ledger, match withdrawal, amount, currency, recipient, and timing; compare audit history. | For `ACTION_REQUIRED`, Admin **Reconcile** can mark verified Stripe/PayPal settlement paid. A terminal `FAILED` with late settlement needs manual investigation and a new guarded backend action; no current Admin action promotes it to paid. Do not release or send again. |
| E. Manual IBAN sent, settlement uncertain | Check bank transfer reference, debit/credit confirmation, destination, amount, return notices, and Partner receipt evidence. | Record **Uncertain** with evidence; keep reservations. Use **Confirm settlement** only after verified receipt. Do not cancel as unsent or issue another bank transfer. |
| F. Manual bank transfer returned | Obtain bank return transaction/reference, full amount, beneficiary, and bank evidence that funds were credited back. | Admin **Record verified bank return** stores one encrypted evidence record while the original `PAID` payout and commissions remain intact. No earnings are restored until a separate accounting design is approved and tested. |
| G. Refund or dispute during processing | Inspect Payment/refund record, current Stripe dispute, reservation, dispatch timestamps, and provider settlement. | Before dispatch, the service blocks processing. After dispatch, reconcile provider outcome first; contingent reversal/debt stays associated with the payout. Keep hold if unsettled. Never remove the hold solely because a webhook arrived late. |
| H. Conflicting webhook/provider evidence | Compare signed webhook event log, current provider object, provider ledger, account, amount, recipient, and audit timestamps. | Current provider object drives ordinary reconciliation; terminal conflicts are audited for review. Keep the reservation and escalate when evidence conflicts. Do not overwrite a historical outcome or send again. |

For **all** cases, commission release requires conclusive no-payment evidence, a separate approved and tested release transaction, and checks for debt, refund, disputes, and any concurrent settlement. Mark `PAID` only through verified provider settlement or the manual bank confirmation with evidence. A new transfer is **never** permitted by the current reconciliation UI after dispatch starts.

## Exact configuration to verify, not enable here

| Setting | Required condition and safe default |
| --- | --- |
| `PARTNER_PAYOUT_MODE` | Absent/other = weekly; `cashout` blocks all new weekly runs, including forced ones. Switch only after weekly in-flight reconciliation. |
| `PARTNER_CASHOUT_REQUESTS_ENABLED` | Exact `true` permits requests only in cash-out mode. Absent/false disables requests. |
| `PARTNER_CASHOUT_PROCESSING_ENABLED` | Exact `true` plus request flag and cash-out mode permits Admin dispatch. Absent/false disables processing. |
| `PARTNER_CASHOUT_RECONCILIATION_ENABLED` | Exact `true` permits Admin reconciliation and secret-authenticated historical PayPal polling without permitting new payout initiation. Absent/false disables the optional reconciliation actions. Signed Connect webhooks remain independent. |
| `PAYOUT_DATA_ENCRYPTION_KEY` | Stable secret required to read existing encrypted destinations/evidence; rotate only with a planned re-encryption procedure. |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONNECT_WEBHOOK_SECRET` | Provider key and separate webhook secrets for live environment. Missing webhook secret rejects delivery. Verify Connect destination and event subscriptions. |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_PAYOUTS_ENABLED`, `PAYPAL_MODE` | PayPal requires credentials and exact `true`; `PAYPAL_MODE=live` chooses live API, otherwise sandbox. Check mode and credentials together before processing. |
| `PAYOUT_JOB_SECRET` | Required for internal weekly run route; missing secret rejects calls. Verify live scheduler and secret storage. |
| `DATABASE_URL`, `DATABASE_SCHEMA_SYNC`, `BOOTSTRAP_BUNDLED_DATA`, `RAILWAY_VOLUME_MOUNT_PATH`, `APP_DATA_ROOT` | Determine which persistent SQLite file and schema procedure the hosted process actually uses. Hosted startup defaults to migrate; `DATABASE_SCHEMA_SYNC=push` changes behavior. Avoid accidental seed/bundled DB replacement. |

Do not include actual secret values in tickets, reports, logs, or screenshots.

## Staged deployment plan (requires separate authorization)

1. Freeze financial configuration changes. Capture deployed commit, live scheduler/jobs, in-flight weekly payouts, webhook health, production migration history, schema, row counts, and provider references. Export a verified, restorable database backup and test restoring a copy.
2. Resolve the migration-chain gap and rehearse the exact proposed sequence on the restored copy. Compare migration checksums, Prisma schema, foreign keys, counts, and financial diagnostic before/after. Obtain approval for any production data or migration-history change.
3. Merge the reviewed branch on GitHub, deploy on Railway with the existing **weekly** mode and both cash-out flags disabled. Verify deployed commit and that webhooks, sign-in, Partner/Admin pages, and old payout reconciliation work. No live payout smoke test is authorized here.
4. Apply approved migrations in a controlled window with a fresh backup and post-migration read-only checks. Keep cash-out disabled. Roll back code if startup fails; restore the database only under a separate incident plan after checking in-flight provider activity.
5. Reconcile all historical weekly payouts, ambiguous disputes, outstanding debt, and provider failures. Verify scheduler config and arrange shutdown of new weekly initiation. Keep historical webhook handling and an explicit PayPal reconciliation route/plan operational.
6. Set `PARTNER_PAYOUT_MODE=cashout` while request and processing flags remain false. Verify scheduled endpoint and Admin force-run return `skipped`, including direct authenticated route calls. Then disable the external weekly scheduler under approved operations control.
7. Enable **requests only** after destination setup, encryption, diagnostic, UI/mobile, and support readiness checks. Monitor atomic reservations and balances.
8. Enable **processing** only after provider and manual reconciliation gaps are resolved. Observe one approved small withdrawal end-to-end, its exact provider reference, settlement, webhook idempotency, ledger state, and Partner display before broadening access.

## Rollback principles

Disable **processing** first, then **requests**, to stop new dispatch. Keep reconciliation enabled only under an approved operator plan so Admins can review in-flight Stripe, PayPal, and manual outcomes while dispatch remains paused. Signed Stripe Connect webhooks continue independently; the historical PayPal polling route requires its own flag and job secret. Keep the cash-out mode until every dispatched withdrawal and old weekly payout has an authoritative outcome; switching back to weekly can create new payouts against unresolved reservations or debt. Do not erase withdrawal, payout, commission, audit, or webhook rows. Do not replay an external payout because a request timed out. If code rollback is needed, verify the old code can read the migrated schema and that signed webhooks still reconcile in-flight payouts; otherwise use a forward fix. Restore a database backup only after reconciling every provider action since the backup, with finance/operations approval, or records may be lost while money moved.
