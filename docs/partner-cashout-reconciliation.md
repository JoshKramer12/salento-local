# Cash-out reconciliation and accounting safeguards

Status: local implementation and mocked-provider tests only. No production migration, provider payout, or bank transfer was performed.

## Modes and authority

`PARTNER_CASHOUT_REQUESTS_ENABLED=true` permits new requests only with `PARTNER_PAYOUT_MODE=cashout`. `PARTNER_CASHOUT_PROCESSING_ENABLED=true` additionally permits Admin dispatch. `PARTNER_CASHOUT_RECONCILIATION_ENABLED=true` independently permits Admin reconciliation of existing withdrawals and the secret-authenticated historical PayPal polling endpoint. All three flags default to disabled. The reconciliation flag does not authorize a new Stripe or PayPal transfer, payout, or weekly run. Signed Stripe Connect webhooks continue to reconcile known payouts independently of these flags. New cash-out payout continuation additionally requires the processing flag, because it creates an external payout from an already recorded transfer.

The historical PayPal monitor is `POST /api/internal/partner-payouts/reconcile`, authenticated with `PAYOUT_JOB_SECRET` as a Bearer token. It polls only existing weekly `PROCESSING` records with a stored `providerBatchId`; it never calls a payout creation API. In cash-out mode, a failed/returned item moves to `ACTION_REQUIRED` while its commissions remain reserved. In weekly mode, the prior release behavior remains. This endpoint is not configured on Railway by this change.

Cookie-authenticated withdrawal POST routes require an explicit same-origin `Origin` header. The secret-authenticated internal polling route and signed provider webhooks use their existing non-cookie authentication mechanisms.

## Stripe

For new dispatches, `stripeTransferRecordedAt` is written only after the transfer creation response and local transfer reference are recorded. `payoutDispatchStartedAt` is written before the first payout creation call. A timeout after that marker can be reconciled by querying Stripe but cannot trigger a second payout creation. Existing historical rows retain NULL markers and cannot use the continuation action.

The Admin **Continue existing Stripe payout** action is available only for a new, recorded transfer with no payout attempt marker. The server retrieves the transfer and connected account, checks amount, currency, destination, transfer group, metadata, reversal state, and payout eligibility, and rejects ambiguous payout listings. It rechecks reservation, debt, refund, dispute, and payment attribution in a transaction, durably claims the payout attempt, then uses the original request-based payout idempotency key. A crash after the claim leaves the request blocked for reconciliation. The action never creates a second transfer.

A provider-reported failed/canceled payout remains `FAILED` with its commissions reserved. If later authoritative provider status conflicts with the local terminal state, the conflict is recorded once in the audit trail and shown for review; the terminal financial status is not silently overwritten.

## PayPal

The deterministic `sender_batch_id` is recorded before the API call. If the response times out without a batch ID, the request remains held. An Admin can attach a batch ID found in PayPal records only when the current provider response matches the batch ID, sender batch ID, single recipient, item ID, amount in cents, and currency. Ordinary reconciliation checks the same attribution before applying a provider status. The attachment action is read-only toward PayPal and does not resend funds. If the batch cannot be found or attribution is incomplete, the hold remains for manual investigation. PayPal documents duplicate protection for a sender batch ID within 30 days; this code does not use a new identifier or automatically retry a timed-out payout. See [PayPal Payouts documentation](https://developer.paypal.com/docs/payouts/standard/integrate-api/customize/).

Historical weekly PayPal payouts can be monitored in cash-out mode through the separate endpoint above. The provider batch ID, sender batch ID, item ID, amount, currency, and item count must match the recorded payout before a result is applied. Missing or mismatched attribution moves the payout to `ACTION_REQUIRED` and keeps its commissions reserved. Failed historical items also remain reserved in cash-out mode pending financial review. Late success after a locally failed withdrawal is audited as conflicting evidence rather than changing status or releasing reservations.

## Verified nonpayment and reservation release

Admin **Review nonpayment** is read-only. **Resolve verified nonpayment** repeats the current provider lookup and, in one transaction, checks the original reserved rows, payment attribution, refund and dispute holds, and Partner debt. It releases the same commission rows to `AVAILABLE`, marks the old request and payout `CANCELED`, and records encrypted review evidence. A partial unique audit index allows only one verified release per withdrawal. Neither action creates a provider transfer or payout.

- A never-claimed `REQUESTED` withdrawal can be released when no dispatch marker or reference exists. A Stripe claim explicitly stopped by an ineligible account or a pre-dispatch financial hold can also be released when no dispatch marker or reference exists. A manual request with no recorded bank transfer requires the Admin's documented confirmation. Other legacy Stripe/PayPal processing rows with no marker remain blocked because absence of a reference is not proof of no call.
- A recorded Stripe transfer with no payout attempt can be released only after Stripe reports that transfer fully reversed and no matching payout appears in a complete provider listing. If an attempted payout has no reference, release stays blocked.
- A Stripe payout reported failed or canceled requires full payout attribution **and** full reversal of the underlying transfer. A failed external payout alone does not restore the funds.
- PayPal requires the saved batch ID, complete item attribution, and an item status of `FAILED` (funds not deducted), `RETURNED`, or `REFUNDED` (funds back with the sender). `BLOCKED`, `DENIED`, missing references, incomplete evidence, and pending outcomes remain reserved. The release list follows [PayPal's transaction-status definitions](https://developer.paypal.com/api/payments.payouts-batch/v1/definitions/transaction_enum/).
- A sent manual transfer that was never marked paid may use the verified bank-return record as nonpayment evidence only when the **full** withdrawal amount came back. A partial return remains reserved because the rest may still settle. Such a return is not subtracted from paid totals because the payout was never counted as paid.
- A contradictory late paid/success result after release is audited and creates one negative `DEBT` adjustment keyed to the old withdrawal. It blocks further disbursement. Any re-disbursement already sent before the contradiction requires human recovery review; the code cannot recall external funds.

## Returned paid bank transfers

A verified full or partial return after `PAID` creates one `PartnerManualBankReturn` row with bank reference, actual returned cents, encrypted evidence, Admin actor, and timestamp. An identical repeat is idempotent; a different return conflicts. The bank reference is globally unique across recorded returns; an existing installation must be checked for duplicates before applying that index. This version supports one return event per withdrawal. The original paid payout and commissions remain unchanged. A recovery payout that is itself returned can be credited through the same source-chain checks.

Admin **Approve returned funds** checks the original paid payout and all its paid source commissions, payment status, refund/dispute holds, and Partner debt. Approval creates one positive `ADJUSTMENT` ledger row with a unique `bank-return-credit:<return-id>` source key and amount equal to the verified return. It has no `earnedAt` and is excluded from total earned commission. The cash-out request transaction can reserve this adjustment with ordinary available commissions; weekly payout selection still accepts only `COMMISSION`. Pre-dispatch checks repeat the return, refund, dispute, debt, and reservation checks. Verified settlement marks the recovery adjustment paid while preserving the first payout. A partial credit below the cash-out minimum waits until the total eligible balance reaches that minimum.

The Partner balance reports gross payouts, verified returns, and net paid (`gross payouts − returns`). An approved return credit is available or processing, never newly earned. An unapproved return is held. Duplicate approval returns the original credit, and the unique source key prevents a second credit. Later debt, refund, or dispute removes an unpaid credit from the available balance and blocks dispatch. If the recovery payout already settled, existing reversal/debt records remain authoritative.

These flows are tested only with disposable SQLite databases and mocked providers. Before launch, provider terminal-status semantics, bank evidence procedures, Railway migration state, and the intended handling of any second partial return on one withdrawal still require controlled review. Do not use a new provider identifier or an Admin override to work around uncertain settlement.
